# LLM Instructions for DirectorSyncV3

## 1. Purpose

This document defines how any Large Language Model (LLM) should behave when
interacting with the **DirectorSyncV3** project. It applies to:

- code generation,
- documentation,
- design discussions,
- refactoring,
- troubleshooting.

The goal is to ensure **consistent, safe, and high-quality assistance** that
respects the project architecture and constraints.

---

## 2. Project Context (Short Reminder)

DirectorSyncV3 is a **generic synchronization engine** for **Logpoint Director**.
It replaces legacy Excel importers with:

- a **SQL database** as the desired state,
- **YAML resource profiles** for per-resource configuration,
- **transformers** (generic and resource-specific) for preprocessing and
  postprocessing,
- a **universal synchronization pipeline** implemented in the `lp_sync` package.

The first focus resources are:

- `repos`
- `routing_policies`

---

## 3. Language and Tone

- All code, comments, docstrings, and documentation generated by the LLM
  must be in **English**.
- The tone should be:
  - clear,
  - concise,
  - professional,
  - slightly opinionated when giving recommendations (explain why).
- Avoid marketing or “fluffy” wording. Prefer actionable, technical content.

---

## 4. Architectural Guardrails

The LLM must **respect and preserve** the following architectural principles:

1. **Single generic Sync Engine**
   - No new “one-off” importer classes.
   - Behaviour is driven by **YAML resource profiles** + **transformers**.

2. **Database-driven desired state**
   - Desired configuration is read from SQL tables.
   - Excel files are considered legacy input, only used by migration scripts.

3. **YAML profiles as the source of configuration behaviour**
   - For each resource:
     - data source,
     - Director API endpoints,
     - field mapping,
     - comparison rules,
     - pre/post transformer pipelines.

4. **Transformers**
   - Small composable units:
     - generic (reusable across resources),
     - resource-specific (logic for a single config type).
   - Execute deterministically and must be idempotent.

5. **Idempotent sync**
   - Running the sync twice with the same desired state must not produce
     additional changes.
   - The LLM must avoid patterns that break idempotence.

---

## 5. Coding Rules for the LLM

When generating or editing code:

1. **Follow PEP 8** (spacing, naming, imports).
2. **Use type hints** everywhere (function parameters and return types).
3. **Add docstrings** on:
   - modules (top-level),
   - public classes,
   - public methods and functions.
4. **Be self-documented**:
   - choose meaningful names,
   - prefer small focused functions,
   - add short comments for non-obvious logic.

5. **Error handling**
   - Never swallow exceptions silently.
   - Raise meaningful custom exceptions where appropriate (e.g. `SyncError`,
     `ProfileError`, `DataSourceError`, `DirectorApiError`).
   - Log errors with enough context (resource name, tenant, key).

6. **Logging**
   - Always use the project logging helpers (or `logging.getLogger`) and
     structured messages.
   - Do not use `print()` in library code.

7. **Tests**
   - Whenever the LLM introduces non-trivial logic, propose or update tests
     (pytest style).

---

## 6. How to Answer User Requests

### 6.1 General approach

When the user asks for help:

1. Clarify the intent in your own reasoning (even if not asked).
2. Respect existing architecture and files (do not reinvent another framework).
3. Prefer incremental changes over “big bang” rewrites.
4. Explain briefly the rationale behind non-trivial changes.

### 6.2 Code Generation

When generating code:

- Provide **complete, runnable modules or functions**, not isolated fragments
  with missing imports.
- Ensure imports are correct relative to the `lp_sync` package structure.
- Keep new files in the appropriate folders:
  - `lp_sync/core/` for engine building blocks,
  - `lp_sync/transformers/` for transformers,
  - `lp_sync/profiles/` for YAML profiles,
  - `lp_sync/utils/` for helpers.

If something must be left as a placeholder, **explicitly mark it** with
comments and docstrings.

### 6.3 Documentation

When generating documentation:

- Use Markdown (`.md`),
- Prefer clear headings and bullet lists,
- Keep sections focused and not excessively long,
- Make documents directly usable in the repository (no “chatty” tone).

---

## 7. Things the LLM Must Avoid

The LLM **must not**:

- Introduce a completely new architecture that conflicts with:
  - the generic Sync Engine,
  - YAML resource profiles,
  - transformer pipelines.
- Add multiple ways to do the same thing without strong justification.
- Use non-English in code, comments or docs (French allowed only in user-facing
  chat explanations, not stored in the repo).
- Hard-code environment-specific paths, tokens, or secrets.
- Add external dependencies without explicit user approval.

---

## 8. Safety and Limitations

- The LLM does not have direct access to production Director or real data.
- Any example configuration or SQL must be **generic** and must not contain
  sensitive information.
- When in doubt, suggest a safe, explicit configuration that the human
  developer can adapt.

---

## 9. Summary

In short, the LLM should:

- think in terms of **Sync Engine + YAML profiles + transformers**,
- write **English-only**, PEP-8, fully typed, well-documented code,
- avoid one-off shortcuts that break the architecture,
- help iterate gradually and safely on DirectorSyncV3.
